# flake-tracker — C07 / L68 score-3 evidence

This directory holds the **score-3 flake-tracker dashboard source data** for
`C07 / L68` (Flake detection).

The sharecli flake policy (`docs/testing/flake-policy.md`) defines a flake as
"a test that passed after failing during a CI run" — i.e. retry-then-pass.
Plan 795 (T-900) ships the tooling that detects this signal automatically
from cargo-nextest JUnit output and produces a JSON report + console
summary.

## Files

| File | Role |
|------|------|
| `flake-report.json` | Latest run's report (JSON). Generated by CI; may be missing locally if the workflow has not run yet. |
| `baseline.json` | Known / accepted flakes. Empty by default; entries are added only when a flake has been triaged and quarantined per `docs/testing/flake-policy.md`. |
| `README.md` | This file. |

## How the tracker works

The tracker consumes any number of cargo-nextest JUnit XML files (the
default CI path writes one per test binary under `target/nextest/ci/`).
It aggregates per-testcase stats across files, classifies each case as
`flaky | regression | stable | skipped`, and emits:

1. **`flake-report.json`** — the JSON document CI uploads as an artifact.
2. **Console summary** — a color-gated (or NO_COLOR-respecting) summary
   listing each flaky test with its `classname::name`, run count, and
   pass/fail breakdown.

## Local usage

```bash
# After running cargo nextest with --profile ci (which writes junit.xml):
just test-nextest

python scripts/flake_tracker.py junit.xml
# -> audit/.flake-tracker/flake-report.json
# -> console summary

# Compare against the baseline:
python scripts/flake_tracker.py 'target/nextest/ci/*.xml' --quiet
# -> exits 0 unless --fail-on-flake is passed
```

## CI integration

`.github/workflows/flake-tracker.yml` runs after every PR CI run. It:

1. Collects all `target/nextest/ci/junit-*.xml` files.
2. Runs `scripts/flake_tracker.py` with the default output path.
3. Uploads `audit/.flake-tracker/flake-report.json` as a build artifact.
4. Posts a comment on the PR when new flakes are introduced vs. baseline.

The job is **advisory** (continue-on-error: true). The flake-tracker
is a signal, not a gate — flake handling is per `docs/testing/flake-policy.md`.

## Acceptance gate

`tests/c07_l68_flake_tracker.rs` exercises the tracker:

1. Parses a synthetic JUnit XML file containing a flake signal and asserts
   the case is classified as `flaky`.
2. Parses a synthetic JUnit XML containing a hard regression and asserts
   the case is classified as `regression`.
3. Parses a baseline JSON file and asserts the baseline-diff logic
   correctly identifies introduced / resolved / persistent flakes.
4. Asserts the JSON report file is written to the configured path.
5. Asserts `--fail-on-flake` exits 1 when a flake is present, 0 otherwise.
6. Asserts NO_COLOR is respected (no ANSI codes in summary output).

These tests are FR-003 acceptance gates for Plan 795.
